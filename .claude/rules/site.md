# Marketing Site (docs/)

`docs/` is the public marketing + docs site served at **viboplr.com** (GitHub Pages; `docs/CNAME`). It is **separate from the Tauri app UI** — editing the site never changes the app, and vice versa. Plain HTML/CSS/JS, no build step. **One stylesheet for every page, `css/plain.css`**: system fonts, one column (`body.wide` widens it for the galleries and the plugin API tables), light + dark through `prefers-color-scheme`, no animation, no web fonts, no gradients. Every page carries the same header (Download · Features · Plugins · Help · Changes · GitHub) and footer. The old `css/style.css` (Outfit, gradient wordmark, reveal animations) is deleted — don't bring it back. `plain.css` also styles the class names other code emits: `gallery-*` (`js/gallery.js`), `timeline-*` (`bump.mjs`'s changelog entries), and the `docs-*` / `api-*` / `install-*` / `session-*` markup in the reference pages.

**Deploy timing:** `pages.yml` deploys any `docs/**` push to main immediately — **except** release commits (`release: vX.Y.Z`), which it skips; for those, `release.yml`'s `deploy-site` job dispatches the Pages deploy only after **both** platform installers have built and uploaded, so the live site never links assets that don't exist yet. Don't remove the `if` guard in `pages.yml` or the `deploy-site` job without the other — each is half of that handshake.

## Positioning (owner decision, 2026-11-13: plain and short)

The home page says what the app does, in plain factual sentences, and stops. **No slogans, no motto, no persona cards, no mock chats, no "Ready to try?"** — the earlier "Your music. Your AI." page was rewritten for reading as over-advertised. Rules for any copy on it:

- One claim per sentence, each one checkable in the app. No adjectives doing the selling ("powerful", "seamless", "blazing"), no numbers that aren't facts of the app.
- Ownership comes first: local folders and Subsonic/Navidrome in one library is the opening line.
- **Three things are surfaced right after the intro** (owner decision, 2026-11-13), as a three-column `points` row and then a section each: **Fast and light** (`#fast` — Rust, SQLite, the system webview, the ~30 MB download, the reproducible search benchmark), **Plugins** (`#plugins` — what a plugin is and what it can add) and **AI control and the control API** (`#ai` — the local MCP server *and* the plain HTTP API, described as off by default, with its switches). Speed claims stay measurable: name the benchmark that produced a number, or leave the number out.
- "Built with AI" is one line in "Good to know" linking `story.html`.
- Say what it doesn't do as plainly as what it does ("It does not come with music").
- The repository `README.md` follows the same rules and the same order: one-paragraph description, then the three points (fast and light, plugins, AI control and the API), then a short "What it does" list that defers to `features.html`.

## Pages

- **`index.html`** — home page. Order: intro (name, one-paragraph description, the two download buttons, `version-badge`, hero screenshot) → the three `points` → `#fast` → `#plugins` → `#ai` → one section per user-facing feature (`#library`, `#playback`, `#radio`, `#lyrics`, `#tags`, `#mini-player`) with a sentence or two and one real screenshot/video → "Good to know" → footer. **Hand-written.** `scripts/bump.mjs` only rewrites its version badge at release; the copy is manual. Settings are linked to their `help.html#<id>` sections rather than explained. Section ids are link targets (the `for/` redirects land on them), so keep them.
- **`for/<persona>.html`** — the old per-audience pages, now **redirect stubs** (`meta refresh` to the matching home section), kept because they had inbound links. Don't write persona pages again; a new audience gets a sentence on the home page, not a page.
- **Site media** is captured from the real, running app by `npm run capture:media` (`scripts/capture-site-media.mjs`, scenes in `scripts/lib/captureScenes.mjs`, pinned by `src/__tests__/captureScenes.test.ts`). It drives the app through the control API's UI verbs (`/v1/ui/navigate`, `/v1/ui/action`, window geometry) and captures with the OS's own tools — macOS: `screencapture -l<windowId>` (stills) and ffmpeg's avfoundation grab cropped to the window (videos); Windows: ffmpeg `gdigrab` cropped to the window's **`client`** rect for both (not `frame`: `GET /v1/window`'s `frame` is outer position + inner size so `window.set` round-trips it, and on Windows the outer position includes an invisible ~8px resize border — cropping to it put a strip of desktop down the left edge), with WebP from `cwebp` or ffmpeg's `libwebp` (per-platform command lines in `scripts/lib/capturePlatform.mjs`, pinned by `src/__tests__/capturePlatform.test.ts`). On Windows the grab is a desktop crop, so nothing may cover the window (Windows can refuse the focus request), and `--grab-scale 1` exists for an ffmpeg that sees logical rather than physical pixels. The window is brought to the front for **every** scene, stills included: macOS stops painting a WKWebView whose window is covered, so a background `screencapture -l` returns the frame from before the navigation (measured — every still of the first run was the previous page). Each scene is checked against `GET /v1/ui` before capture and skipped if the page didn't land; window, skin, hero look, volume and playback are restored afterwards. Output goes to `docs/assets/media/` (`<id>.webp`, or `<id>.mp4` + `.webm` + `-poster.webp`, muted). A `grid` scene (`mini-player-sizes`) grabs the mini player at every layout × width (set through `window.set`'s `miniSize` / `miniWidth`) and composes one transparent WebP, each cell inset 1px and corner-masked because the grab is a desktop crop and the window's rounded corners hold whatever sat behind it. **Capture the site from the demo library, never from a real profile** (see the next bullet) — the first published set was cut from the owner's own profile and put their whole collection, listening history and likes on a public page. Review the files before committing either way; `--redact "name=you,Other"` hides account names and personal titles through showcase's redaction for the whole run, and the Spotify scene scrolls past its personal greeting heading. The mini sizes persist and are restored at the end of the run, like the window and skin. Scenes that need outside services (a signed-in Spotify, a real download, the Claude app) are listed as `MANUAL_CAPTURES` and printed at the end of every run. On a page, a video goes in as `<video autoplay muted loop playsinline poster>` with the webm source first.
- **YouTube Shorts** (`npm run short -- --demo ~/ViboplrDemo`, `scripts/make-short.mjs`; scenarios in `scripts/lib/shorts.mjs`, pinned by `src/__tests__/shorts.test.ts`; the per-persona plan is `docs/brainstorms/2026-10-24-youtube-shorts-scenarios-requirements.md`). Same rules as the site media, from the same runner (`scripts/lib/captureRunner.mjs`, shared with `capture-site-media.mjs`): demo library only, window to the front, state restored. A short records the **whole** window while timed beats drive the app — including on-camera clicks and typing through the control API's generic input (`POST /v1/ui/input`, which draws its own cursor and needs the demo profile's **Click and type** switch) — then a virtual camera (`zoompan` over the window letterboxed on a blurred copy of itself) follows each beat's focus, captions are rendered as PNGs by the e2e suite's Chromium (this ffmpeg has no `drawtext`) and burned in, and an end card is appended. Output is **silent** by default (`--music` mixes a bed you have the rights to); it goes to `~/ViboplrShorts`, not the repo. The collectors' short repairs the demo library's deliberately mis-tagged compilation (*Late Night Drive*, no ALBUMARTIST — `demoCatalog.mjs` `COMPILATIONS`), so its take (the only one with `needs: "compilation"`) first regenerates its tags (`make-demo-library` treats a drifted `album_artist` as stale) and rescans until it is split again.
- **`examples/mcp-session.html`** — a real Claude + MCP session written up step by step (the listener's own words, what happened, which tools), linked from the home page's AI control section. **Hand-written.** It is anonymized on purpose: no play counts, paths, likes or account/sharer names, and the download source is "a download plugin", never a named peer-to-peer network. Keep it that way when editing; session-specific track counts are fine. One level deep, so links start with `../`; its styles are the `session-*` block in `css/plain.css`.
- **`features.html`** — the full feature list, plain grouped bullets with no screenshots (the home page has those). **Generated — never hand-edit as the only change.** The template lives in `scripts/lib/features.mjs` (shared by `bump.mjs` Step 6 and `scripts/regen-features.mjs`); `bump.mjs` overwrites the page from `features.json` on every release.
- **`features.json`** — **source of truth for the features page**: a list of groups `{ id, title, items[] }`. Each item is one plain, checkable sentence, injected as **raw HTML** (links, `<code>` and the plugin tag render). `id` is the section anchor. After editing, run `node scripts/regen-features.mjs` so the two don't drift before a release.
- **`plugins.html` / `skins.html`** — gallery pages; entries load dynamically from the gallery repos via `js/gallery.js` (nothing to hand-edit per plugin/skin). Each page sets `window.VBPL_GALLERY` and keeps the element ids `gallery.js` looks up (`galleryGrid`, `galleryStatus`, `gallerySearch`, `galleryCount`, and on plugins.html the `galleryRecommended*` / `galleryAllTitle` / `galleryExperimental*` group). plugins.html also has short hand-written "Write a plugin" / "Add it to the gallery" steps.
- **`community.html`** — the **Community** nav entry. **Hand-written and static (owner decision, 2026-10-16): it only explains Vibo Community and sends people to `community.viboplr.com`** (repo `outcast1000/viboplr-community`). It does not list, search or fetch anything from the community server, and it carries no plugin install steps (one line names the Vibo Community plugin and where it is in the app); browsing, sharing and signing in all happen on the community site. Do not bring back a live listing (the old `js/community.js` module shell was removed). The sections keep the ids `music`, `mixtapes`, `servers`, because `community.html#servers` is linked from **`servers.html`** (kept as a redirect, since the old public server directory had inbound links).
- **`plugin-dev.html`** — plugin developer documentation. **Hand-written**, not bump-generated: quickstart (manifest + index.js), local dev (dev plugin folder), contribution points, the full `api.*` reference (all namespaces from `src/types/plugin.ts`), sandbox rules, and package/publish steps (`update.json` schema from `models.rs::UpdateInfo`). When the plugin API surface changes (`src/types/plugin.ts` / `.claude/rules/plugins.md`), update this page's API tables in the same change.
- **Demo library** (`npm run demo:library -- --out ~/ViboplrDemo` → `npm run demo:setup -- --music ~/ViboplrDemo` → `npm run capture:media -- --demo ~/ViboplrDemo`): the library the site is captured from. **Well-known albums, synthesised audio** — 2–3 records per decade picked in `scripts/lib/demoAlbumPicks.mjs`, tracklists + durations fetched once from MusicBrainz by `scripts/fetch-demo-tracklists.mjs` into the committed `demoAlbums.mjs` (the generator never touches the network, so a rebuild is identical offline); ffmpeg `aevalsrc` makes the audio, with verse/chorus sections so the waveform seek bar reads as music. Covers, artist photos, bios and listener counts come from the **app's own providers**, as for any user — setup pre-requests every image, spaced out, and clears `image_fetch_failures` on its last quit so a miss is retried during capture. **Real lyrics are copyrighted and never shown**: setup switches off the online lyrics plugins (the bundled `lyrics` plugin — LRCLIB + Lyrics.ovh — and genius), and the lyrics scenes play the one **invented** album (Glass Harbour, `art: true` — procedural folder art from `demoArt.mjs`, original sidecar `.lrc`). `tags[0]` of each pick is the genre written to the files and is a shared family on purpose, or radio builds one-artist stations. History is keyed with `canonicalName` (= the app's `strip_diacritics(to_lowercase())`; real titles carry accents). Pinned by `src/__tests__/demoCatalog.test.ts`. `setup-demo-profile.mjs` loads it into the **`perf-demo`** profile (the probe route only answers on `perf` / `perf-*`; `VIBOPLR_PROBE_PROFILE` points `appControl.mjs` at it) — history goes straight into the `history_*` tables with the app stopped, since history is keyed by artist/title and has no write route. `--demo` also switches on `SCREENSHOT_SCENES` (regenerating `docs/assets/screenshots/` under the names the pages already link to), forces the queue panel open, redacts the home folder from on-screen paths, and holds the display awake (`caffeinate`) — a display that sleeps mid-run turns every later grab into a failure.
- **`help.html`** — plain-language explainers for in-app settings/features (exclusive audio, playback engine, ReplayGain, profiles, …). **Hand-written**, not bump-generated. Section `id`s are linked from inside the app (the `HelpLink` "?" icons in Settings open `help.html#<id>`; base URL in `src/constants/links.ts`), and older app builds link into the live page — so ids are **add-only**: never rename or remove one. When adding a `HelpLink` in the app, add the matching section here in the same change.
- **`jaangle.html`** — reference page for Jaangle (first named TeenSpirit), the owner's C++ Windows player from 2003–2010 that many of Vibo's ideas come from; source at `outcast1000/TeenSpirit`. **Hand-written**, linked from `story.html` and the home page's "Good to know". Its facts come from that repo (README, source tree, `Documents/` notes); the "What Vibo took from it" table pairs only features that exist on both sides — check the repo before adding a row.
- **`download.html`, `support.html`, `story.html`, `history.html`** (changelog; the page shell is hand-written, entries are prepended by bump at the `<div class="timeline" id="timeline">` marker). download.html also has a **beta-builds section** that is populated client-side from the GitHub releases API when the newest release is a prerelease (hidden otherwise) — beta releases never rewrite the site (`bump.mjs` skips all site steps for hyphenated versions), so this section must stay dynamic; don't convert it to bump-written static links.

**Every local link is checked.** `src/__tests__/siteLinks.test.ts` fails when any page (all but `history.html`) links a file, asset or `#anchor` that doesn't exist, or when a `for/` stub stops redirecting to the home page.

## Core vs. plugin on the site

The app is an **orchestrator**: streaming services and most metadata are **plugins**, not core (see `plugins.md`). Anything plugin-powered must be presented as such on the site — tag the bullet with `<span class="feature-tag">plugin</span>` (styled in `css/plain.css`). Do **not** advertise plugin capabilities as core (e.g. the home hero must list only local folders / Subsonic / Navidrome as built-in sources — **not** Spotify/YouTube).

- **Core:** local folders, Subsonic/Navidrome, playback (gapless/crossfade/native A·V), queue, likes, playlists + mixtapes, Home (radio carousel + shelves), Now Playing (synced lyrics + video theater), Radio + auto-continue, FTS5 search, skins, mini player, keyboard shortcuts, downloads framework, profiles, the plugin system itself.
- **Plugin (tag as such):** Last.fm (scrobble / history import / similar / bios / community tags), lyrics (LRCLIB · Lyrics.ovh · Google), artwork (TheAudioDB · Deezer · iTunes · MusicBrainz · Google Images), Genius (song explanations), Spotify browse, YouTube play + download (yt-dlp). (P2P sharing is **gone** — the host libp2p engine was removed and the plugin de-registered from the gallery; don't re-add it to the site's feature copy.)
