# Marketing Site (docs/)

`docs/` is the public marketing + docs site served at **viboplr.com** (GitHub Pages; `docs/CNAME`). It is **separate from the Tauri app UI** — editing the site never changes the app, and vice versa. Plain HTML/CSS/JS, no build step, single font (Outfit) and a pink→magenta `gradient-text` wordmark as the established brand identity.

**Deploy timing:** `pages.yml` deploys any `docs/**` push to main immediately — **except** release commits (`release: vX.Y.Z`), which it skips; for those, `release.yml`'s `deploy-site` job dispatches the Pages deploy only after **both** platform installers have built and uploaded, so the live site never links assets that don't exist yet. Don't remove the `if` guard in `pages.yml` or the `deploy-site` job without the other — each is half of that handshake.

## Positioning (owner decision, 2026-10-16)

Vibo is **the player for music you own**: local folders and Subsonic/Navidrome servers in one library. That is the headline on the home page, the README and the onboarding wizard. Everything else is a reason to *stay*, never the pitch:

- **AI control (the MCP server) is a feature, not the headline.** It gets its own section below the fold, framed as optional and off by default. Do not put it back in the hero, the `<title>` or the meta description.
- **"Built by AI" is the story, not the product.** It lives in `story.html`, the README's "Built with AI" section and the bottom CTA's story link, never in the hero or the opening pitch. Listeners choose a player for what it does for their music.
- **Three primary audiences:** collectors, self-hosters (Subsonic/Navidrome) and audiophiles. They are the only persona cards on the home page. The other persona pages stay live (they are linked from outside), but appear only as "More ways to use Vibo" links and in each page's "Also for you". A new persona page joins that link row; it does not get a home-page card.

## Pages

- **`index.html`** — home page, in this order: hero → **`#own`** ("Made for the music you own": the three primary audience cards — collectors, self-hosters, audiophiles — in `persona-grid--primary`) → **AI showcase** (`#ai`, labelled "And it talks": mock chat, guardrails, one card per assistant capability; plugin-powered cards keep their `plugin` tag) → **`#for-you`** ("More ways to use Vibo": every other `for/*.html` page as a `persona-links` pill) → "the basics" cards → CTAs. **Hand-written.** `scripts/bump.mjs` only rewrites its version badge and download URLs at release; the copy is manual.
- **`for/<persona>.html`** — one page per listener persona (audiophiles, collectors, spotify, …), linked from the home page (primary cards or the "More ways" links). **Hand-written**, never touched by `bump.mjs`. Same template on every page: `persona-hero` (label + headline + main media) → `feature-section` rows (text + `persona-media`) → "Also for you" (`related-personas`, two other personas) → the shared bottom CTA. Paths are one level deep, so every site-relative `href`/`src` starts with `../`. A media slot is an `<img>`, a muted looping `<video>`, or a dashed `persona-media--pending` placeholder naming the capture still to be made. Keep the copy release-proof: no version numbers, no size/RAM/plugin-count figures, no "new in v1.0.x".
- **Persona media** is captured from the real, running app by `npm run capture:media` (`scripts/capture-site-media.mjs`, scenes in `scripts/lib/captureScenes.mjs`, pinned by `src/__tests__/captureScenes.test.ts`). It drives the app through the control API's UI verbs (`/v1/ui/navigate`, `/v1/ui/action`, window geometry) and captures with the OS's own tools — macOS: `screencapture -l<windowId>` (stills) and ffmpeg's avfoundation grab cropped to the window (videos); Windows: ffmpeg `gdigrab` cropped to the window's **`client`** rect for both (not `frame`: `GET /v1/window`'s `frame` is outer position + inner size so `window.set` round-trips it, and on Windows the outer position includes an invisible ~8px resize border — cropping to it put a strip of desktop down the left edge), with WebP from `cwebp` or ffmpeg's `libwebp` (per-platform command lines in `scripts/lib/capturePlatform.mjs`, pinned by `src/__tests__/capturePlatform.test.ts`). On Windows the grab is a desktop crop, so nothing may cover the window (Windows can refuse the focus request), and `--grab-scale 1` exists for an ffmpeg that sees logical rather than physical pixels. The window is brought to the front for **every** scene, stills included: macOS stops painting a WKWebView whose window is covered, so a background `screencapture -l` returns the frame from before the navigation (measured — every still of the first run was the previous page). Each scene is checked against `GET /v1/ui` before capture and skipped if the page didn't land; window, skin, hero look, volume and playback are restored afterwards. Output goes to `docs/assets/media/` (`<id>.webp`, or `<id>.mp4` + `.webm` + `-poster.webp`, muted). A `grid` scene (`mini-player-sizes`) grabs the mini player at every layout × width (set through `window.set`'s `miniSize` / `miniWidth`) and composes one transparent WebP, each cell inset 1px and corner-masked because the grab is a desktop crop and the window's rounded corners hold whatever sat behind it. **Capture the site from the demo library, never from a real profile** (see the next bullet) — the first published set was cut from the owner's own profile and put their whole collection, listening history and likes on a public page. Review the files before committing either way; `--redact "name=you,Other"` hides account names and personal titles through showcase's redaction for the whole run, and the Spotify scene scrolls past its personal greeting heading. The mini sizes persist and are restored at the end of the run, like the window and skin. Scenes that need outside services (a signed-in Spotify, a real download, the Claude app) are listed as `MANUAL_CAPTURES` and printed at the end of every run. On a page, a video goes in as `<video autoplay muted loop playsinline poster>` with the webm source first.
- **YouTube Shorts** (`npm run short -- --demo ~/ViboplrDemo`, `scripts/make-short.mjs`; scenarios in `scripts/lib/shorts.mjs`, pinned by `src/__tests__/shorts.test.ts`; the per-persona plan is `docs/brainstorms/2026-10-24-youtube-shorts-scenarios-requirements.md`). Same rules as the persona media, from the same runner (`scripts/lib/captureRunner.mjs`, shared with `capture-site-media.mjs`): demo library only, window to the front, state restored. A short records the **whole** window while timed beats drive the app — including on-camera clicks and typing through the control API's generic input (`POST /v1/ui/input`, which draws its own cursor and needs the demo profile's **Click and type** switch) — then a virtual camera (`zoompan` over the window letterboxed on a blurred copy of itself) follows each beat's focus, captions are rendered as PNGs by the e2e suite's Chromium (this ffmpeg has no `drawtext`) and burned in, and an end card is appended. Output is **silent** by default (`--music` mixes a bed you have the rights to); it goes to `~/ViboplrShorts`, not the repo. The collectors' short repairs the demo library's deliberately mis-tagged compilation (*Late Night Drive*, no ALBUMARTIST — `demoCatalog.mjs` `COMPILATIONS`), so each take first regenerates its tags (`make-demo-library` treats a drifted `album_artist` as stale) and rescans until it is split again.
- **`features.html`** — the features page. **Generated — never hand-edit as the only change.** The template lives in `scripts/lib/features.mjs` (shared by `bump.mjs` Step 6 and `scripts/regen-features.mjs`); `bump.mjs` overwrites the page from `features.json` on every release, so a manual edit there is lost at the next bump.
- **`features.json`** — **source of truth for the features page.** Edit this to change features. Each entry: `{ group?, groupDescription?, label, heading, description, items[], screenshot, screenshotAlt, screenshotWidth?, screenshotHeight? }`.
  - `description`/`items` are injected as **raw HTML** (entities like `&amp;`/`&mdash;` and inline `<span>`s render).
  - `group` clusters features under a titled header (rendered when the value differs from the previous entry's, so keep each group's entries contiguous); `groupDescription` is read only on the entry that opens the group.
  - An empty `screenshot` (`""`) renders a graceful "coming soon" placeholder instead of a broken `<img>`. Screenshots live in `docs/assets/screenshots/*.webp`, referenced by filename only (generated by `npm run screenshots`).
  - The skin-gallery block is injected **after the `Skins` feature**, so keep at least one feature after `Skins`.
  - After editing `features.json`, run `node scripts/regen-features.mjs` to regenerate `features.html` so the two don't drift before a release.
- **`plugins.html` / `skins.html`** — gallery pages; entries load dynamically from the gallery repos via `js/gallery.js` (nothing to hand-edit per plugin/skin). plugins.html also carries hand-written "Build your own plugin" / "How to add a plugin" steps strips linking into the developer docs.
- **`community.html`** — the **Community** nav entry. **Hand-written and static (owner decision, 2026-10-16): it only explains Vibo Community and sends people to `community.viboplr.com`** (repo `outcast1000/viboplr-community`). It does not list, search or fetch anything from the community server, and it carries no plugin install steps (one line names the Vibo Community plugin and where it is in the app); browsing, sharing and signing in all happen on the community site. Do not bring back a live listing (the old `js/community.js` module shell was removed). The "What you'll find there" cards keep the ids `music`, `mixtapes`, `servers`, because `community.html#servers` is linked from `for/self-hosters.html` and **`servers.html`** (kept as a redirect, since the old public server directory had inbound links).
- **`plugin-dev.html`** — plugin developer documentation. **Hand-written**, not bump-generated: quickstart (manifest + index.js), local dev (dev plugin folder), contribution points, the full `api.*` reference (all namespaces from `src/types/plugin.ts`), sandbox rules, and package/publish steps (`update.json` schema from `models.rs::UpdateInfo`). When the plugin API surface changes (`src/types/plugin.ts` / `.claude/rules/plugins.md`), update this page's API tables in the same change.
- **Demo library** (`npm run demo:library -- --out ~/ViboplrDemo` → `npm run demo:setup -- --music ~/ViboplrDemo` → `npm run capture:media -- --demo ~/ViboplrDemo`): the library the site is captured from. **Well-known albums, synthesised audio** — 2–3 records per decade picked in `scripts/lib/demoAlbumPicks.mjs`, tracklists + durations fetched once from MusicBrainz by `scripts/fetch-demo-tracklists.mjs` into the committed `demoAlbums.mjs` (the generator never touches the network, so a rebuild is identical offline); ffmpeg `aevalsrc` makes the audio, with verse/chorus sections so the waveform seek bar reads as music. Covers, artist photos, bios and listener counts come from the **app's own providers**, as for any user — setup pre-requests every image, spaced out, and clears `image_fetch_failures` on its last quit so a miss is retried during capture. **Real lyrics are copyrighted and never shown**: setup switches off the online lyrics plugins (the bundled `lyrics` plugin — LRCLIB + Lyrics.ovh — and genius), and the lyrics scenes play the one **invented** album (Glass Harbour, `art: true` — procedural folder art from `demoArt.mjs`, original sidecar `.lrc`). `tags[0]` of each pick is the genre written to the files and is a shared family on purpose, or radio builds one-artist stations. History is keyed with `canonicalName` (= the app's `strip_diacritics(to_lowercase())`; real titles carry accents). Pinned by `src/__tests__/demoCatalog.test.ts`. `setup-demo-profile.mjs` loads it into the **`perf-demo`** profile (the probe route only answers on `perf` / `perf-*`; `VIBOPLR_PROBE_PROFILE` points `appControl.mjs` at it) — history goes straight into the `history_*` tables with the app stopped, since history is keyed by artist/title and has no write route. `--demo` also switches on `SCREENSHOT_SCENES` (regenerating `docs/assets/screenshots/` under the names the pages already link to), forces the queue panel open, redacts the home folder from on-screen paths, and holds the display awake (`caffeinate`) — a display that sleeps mid-run turns every later grab into a failure.
- **`help.html`** — plain-language explainers for in-app settings/features (exclusive audio, playback engine, ReplayGain, profiles, …). **Hand-written**, not bump-generated. Section `id`s are linked from inside the app (the `HelpLink` "?" icons in Settings open `help.html#<id>`; base URL in `src/constants/links.ts`), and older app builds link into the live page — so ids are **add-only**: never rename or remove one. When adding a `HelpLink` in the app, add the matching section here in the same change.
- **`download.html`, `support.html`, `history.html`** (changelog; also bump-generated). download.html also has a **beta-builds section** that is populated client-side from the GitHub releases API when the newest release is a prerelease (hidden otherwise) — beta releases never rewrite the site (`bump.mjs` skips all site steps for hyphenated versions), so this section must stay dynamic; don't convert it to bump-written static links.

## Core vs. plugin on the site

The app is an **orchestrator**: streaming services and most metadata are **plugins**, not core (see `plugins.md`). Anything plugin-powered must be presented as such on the site — tag the bullet with `<span class="feature-tag">plugin</span>` (styled in `css/style.css`). Do **not** advertise plugin capabilities as core (e.g. the home hero must list only local folders / Subsonic / Navidrome as built-in sources — **not** Spotify/YouTube).

- **Core:** local folders, Subsonic/Navidrome, playback (gapless/crossfade/native A·V), queue, likes, playlists + mixtapes, Home (radio carousel + shelves), Now Playing (synced lyrics + video theater), Radio + auto-continue, FTS5 search, skins, mini player, keyboard shortcuts, downloads framework, profiles, the plugin system itself.
- **Plugin (tag as such):** Last.fm (scrobble / history import / similar / bios / community tags), lyrics (LRCLIB · Lyrics.ovh · Google), artwork (TheAudioDB · Deezer · iTunes · MusicBrainz · Google Images), Genius (song explanations), Spotify browse, YouTube play + download (yt-dlp). (P2P sharing is **gone** — the host libp2p engine was removed and the plugin de-registered from the gallery; don't re-add it to the site's feature copy.)
