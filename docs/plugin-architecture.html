How an assistant, the control API, the host and the plugins connect

Everything a plugin can do goes through one api object the host hands it. Everything an AI assistant can do goes through the MCP server, the localhost HTTP API, and the same host registries. The four operations added this week make plugins a third caller of those registries, so a plugin can build on another plugin without a new bus.

The api object every plugin receives

Twenty namespaces, grouped by which way the call goes. Contribute means the plugin registers a handler and the host calls it later. Consume means the plugin calls the host. Compose means the plugin calls another plugin, with the host in between.

Compose

Plugin calls another plugin, host in between
  • plugins.list()id, name, version, enabled, status, capability counts
  • informationTypes.fetch(typeId, entity, { pluginId?, force? }) — cache-first, else the user-ordered provider chain
  • search.listProvidersuser-visible catalog providers, keyed pluginId:providerId
  • search.query(providerKey, query, limit?) → PluginSearchResult
  • assistant.listTools(pluginId?) → roster with schemas and instructions
  • assistant.invoke(pluginId, tool, args?) → the tool's return value
Every compose call: target installed, enabled and active · no cycle in flight · logged as caller → target:what · same 60 s budget as the HTTP path.

Four operations, three callers, one implementation

The MCP tool, the HTTP verb and the plugin method all land on the same host function. That is what keeps an assistant, a plugin and the UI from getting different answers.

Not built on purpose: a pub/sub bus between plugins, and access to another plugin's storage. Request and response through the host covers every case discussed, and the per-plugin storage scoping is a known hole, not a channel.
