How the plugin API, control API and MCP server reach the Rust and JS layers

Vibo has one Rust process and one webview JS context. Plugins run inside that JS context and get an api object. AI assistants connect through the MCP server, which calls a localhost HTTP API in Rust. That API answers some requests from the database directly and sends the rest across IPC to the webview. Both paths end up in the same shared ops modules, which the UI uses too.

Four ways in

Each caller enters at a different layer. Once a request reaches the webview, all of them run through the same hooks and ops.

One assistant request, end to end

This walk-through is play_tracks, a bridged route. A read such as search_library stops at step 3, because Rust answers it from SQLite.

  1. The assistant calls the MCP tool play_tracks over stdio.
    mcp/viboplr-mcp.mjs
  2. The MCP server re-reads control-api.json for the selected profile, then sends an HTTP request to 127.0.0.1:<port>/v1/queue/play with the bearer token. It retries on 503 and 504.
    profile folder · 0600
  3. axum checks the token. The route is bridged, so it registers a oneshot channel under a new request id and emits control-api-request {id, verb, payload}. It returns 503 until the webview has called control_api_client_ready.
    src-tauri/src/control_api.rs
  4. The control bridge maps the verb to queueOps.playNow. Cmd+K plugin results and api.playback use this same function.
    src/hooks/useControlApi.ts → src/utils/queueOps.ts
  5. playNow applies the duplicate policy and like reconcile, then calls useQueue.playTracks → usePlayback → invoke(engine_*) → libmpv.
    useQueue.ts · nativeEngine.ts · mpv_engine/
  6. The webview calls control_api_respond {id, ok, result}. That completes the oneshot, and the HTTP response becomes the tool result. With no answer within 10 s (longer for slow verbs), Rust returns 504.
    commands/app.rs

Where a plugin API call runs

A plugin method either runs entirely in JS, calls into Rust, or answers a call that Rust started.

Runs in JS only

the host calls the plugin's handler directly
  • streamResolvers · the resolver chain in App.tsx
  • downloadProviders · decideDownload → DownloadModal
  • informationTypes · infoFetchChain
  • home.registerShelf · useHome
  • search / assistant · hostOps
  • contextMenu · native menu specs

  • network.fetch · plugin_fetch, no CORS
  • storage · plugin_storage_* (SQLite)
  • storage.files · plugin_files_*, traversal-checked
  • system.exec · plugin_exec, allow-listed binaries
  • scheduler · plugin_scheduler_*
  • library writes · tags, likes, history batches
